Git Collaboration Lab &
Planned Conflict Scenarios

Real-world collaborative projects inevitably experience merge conflicts when team members edit the same lines, alter global styles, or rename and delete shared assets. This lab documents three engineered conflict scenarios, their anatomy in Git, and their systematic resolution.

1. Team Branching Topology

Both Developer A and Developer B branched off the identical commit on main. Independent commits were authored concurrently, producing divergence points that guarantee conflicts upon merging.

Branch: main

Production Baseline

Contains the starter HTML structure, global CSS styles, and base recipes. Both developers branched from base commit Initial Recipe Book.

• Base css/style.css

Scenario 2: CSS Property Conflict

Conflicting Brand Color on .recipe-title in css/style.css

Both developers customized the primary header styling in the shared stylesheet.

Git Conflict Marker in css/style.css CONFLICT (content) in css/style.css

  font-weight: 700;
<<<<<<< HEAD
  color: #2e7d32;
=======
  color: #b45309;
>>>>>>> feature/dinner-recipes
}

✔ Resolution & Arbiter Decision

Decision Rationale: The design team tested both colors with the Web Content Accessibility Guidelines (WCAG). #2e7d32 (Forest Green) maintains a superior contrast ratio of 5.4:1 against light backgrounds and harmonizes with the culinary theme. We also provided hover states to incorporate the warm amber accents.

Resolved Declaration in css/style.css Accessible & Cohesive 
.recipe-title {
  font-family: var(--font-heading);
  font-size: 1.35rem;
  font-weight: 700;
  color: #2e7d32; /* Selected green palette */
  margin-bottom: 0.65rem;
}

Terminal Resolution Commands:

# Inspect the conflict in style.css git status # Open css/style.css, retain color: #2e7d32, and remove the marker lines git add css/style.css git commit -m "Resolve recipe title style conflict: adopt accessible #2e7d32 with warm hover accent"
Scenario 3: Modify vs Delete Collision

Conflict on Shared File recipes/pasta.html

Developer A revised and upgraded the recipe while Developer B deleted the file.

Tree Structural Conflict
Developer A Action Updated & Expanded Content 
// Developer A enhanced recipes/pasta.html:
+ Added Parmigiano-Reggiano measurements
+ Added step-by-step emulsification instructions
+ Added allergen tags & wine pairing notes
File size increased: +1,240 bytes
Developer B Action Deleted File 
// Developer B pruned the directory:
$ git rm recipes/pasta.html
$ git commit -m "Remove legacy pasta draft file"
File status: DELETED
Git Merge Output (Modify/Delete Conflict) CONFLICT (modify/delete) 
Auto-merging recipes/pasta.html
CONFLICT (modify/delete): recipes/pasta.html deleted in feature/dinner-recipes
and modified in HEAD. Version HEAD of recipes/pasta.html left in tree.
Automatic merge failed; fix conflicts and then commit the result.

✔ Resolution & Arbiter Decision

Decision Rationale: Deleting the file was an inadvertent pruning mistake on Developer B's branch. Developer A's revisions contain valuable, tested culinary instructions and rich nutritional data. The maintainer explicitly retains Developer A's modified version of recipes/pasta.html.

File Preservation Verification File Kept & Tracked 
$ git add recipes/pasta.html
$ git status
On branch main
Changes to be committed:
	modified:   recipes/pasta.html

Terminal Resolution Commands:

# In merge conflict state: git status # To KEEP the modified file: git add recipes/pasta.html git commit -m "Resolve pasta recipe modify-delete conflict: retain Developer A's enhanced recipe" # (Alternative: If deletion had been preferred, the command would be: git rm recipes/pasta.html)
GitHub Workflow & Best Practices

GitHub Pull Request (PR) & Code Review Lifecycle

How the team replicates and documents these findings using GitHub Web UI & CLI.

1. Feature Branch Push

Each developer pushes their branch to GitHub:
git push -u origin feature/breakfast-recipes
git push -u origin feature/dinner-recipes

2. PR Review & Merge PR #1

Developer A opens PR #1 to main. Peer review approves breakfast cards. PR #1 merges cleanly with fast-forward or merge commit.

3. PR #2 Conflict Trigger

Developer B opens PR #2 to main. GitHub detects conflicting files: "Can't automatically merge. Don't worry, you can still create the pull request."

4. Synchronize & Clear

Developer B pulls latest main into their local branch, resolves the markers, commits, and pushes. The GitHub PR automatically switches to green "Able to merge"!
